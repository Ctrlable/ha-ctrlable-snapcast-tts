# RTP mic: a Wi-Fi satellite's beam on the server

The XVF3800 satellite answers through the Snapcast TTS add-on, so the reply
plays from room speakers this device never sees as a reference: its hardware
echo canceller has nothing to subtract. The server knows exactly what every
room plays. Stream the beam there and let PipeWire cancel the echo.

```
XVF3800 --I2S--> ESP32 rtp_mic --RTP L16/16000/1, 20 ms--> beta :<port>
                                                      |
                     libpipewire-module-rtp-source ---+--> rtp_mic_<node>
                                                              |
  zonebus_<room>.monitor (music + replies + announcements) ---+--> echo-cancel (WebRTC)
                                                                      |
                                                     aec_mic_<node> --+--> server LVA (optional)
```

The device does not know the server. It runs a small **control service** on
tcp/6055 (`esphome/components/rtp_mic/rtp_session.h`); the hardware manager
("Add network mic", by IP or from the mDNS record `_ctrlable-rtp-mic._tcp`,
TXT `format=L16/16000/1 control=tcp-line/1 beams=asr,wakeword`) connects and
asks for the stream. The RTP goes back to **the address the request came
from**, so nothing is typed on the device and the manager needs no ESPHome API
key.

### Control protocol (one text line per request)

| request | reply |
|---|---|
| `START <udp_port> [beam=asr\|wakeword] [token=<t>]` | `OK STREAMING format=L16/16000/1 pt=96 ssrc=<hex> beam=<b> port=<p>` |
| `KEEPALIVE` | `OK ALIVE` |
| `STOP` | `OK STOPPED` |
| `STATUS` | `OK IDLE` or `OK STREAMING to=<ip>:<port> beam=<b>` |
| anything else | `ERR bad-request` (connection closed) |

- The session lives as long as the TCP connection stays open **and** a line
  arrives at least every 30 s (the manager sends `KEEPALIVE` every 10 s). A
  crashed or unplugged manager stops the stream by itself.
- One session at a time. Another host gets `ERR busy held-by=<ip>`; the same
  host may take over (a restarted manager reconnecting early).
- `rtp_mic_token` (package substitution, default empty) makes `token=` required.
  Empty means anyone on the LAN who reaches tcp/6055 can listen -- the same
  trust given to snapcast and RTP on this network. The token is clear text.
- Device entities: **RTP mic service** (switch, default ON -- nothing streams
  until a server asks; OFF refuses and hangs up at once: the local privacy
  switch) and **RTP mic client** (who is listening, or empty).

Try it by hand: `printf 'START 46001 beam=asr\n' | nc -q 40 <device-ip> 6055`
(the stream stops when `nc` exits or after 30 s without a line).

## Proven on beta (PipeWire 1.4.2), 2026-10-10

A throwaway client-side `pipewire -c` instance received a paced L16 stream
with the exact packet layout of `esphome/components/rtp_mic/rtp_core.h`; the
system stack was not restarted and nothing was linked to any sink.

| `sess.latency.msec` | result |
|---|---|
| 20 | continuous, but the receiver resamples hard to hold it: corr ~0.70 |
| 40 | **bit-exact below 6 kHz** (corr 1.0000, gain 1.000, no gaps) |
| 60 | continuous, slow rate-matching drift (3 samples/s), corr 0.90-0.97 |

Loopback only -- no Wi-Fi jitter. Start the real device at **80** (must be an
integer multiple of the 20 ms ptime) and lower it once loss counts are known;
the device logs `sent/dropped` once a minute.

Other facts measured:
- the receiver binds its UDP port only once something reads the source;
- the source survives the sender stopping (70 s tested) and resumes cleanly,
  so a server LVA bound to it does not lose its mic when the device reboots;
- `source.ip` defaults to the multicast group 224.0.0.56: unicast needs
  `source.ip = 0.0.0.0`;
- echo-cancel in `monitor.mode` captured `zonebus_c0p1h4p3_dining`'s monitor
  beside the room's own link and created no playback node -- read-only on the
  room.

## What the manager generates

NOT a `pipewire.conf.d` drop-in: on this host adding one means restarting the
whole stack, and every room drops out. Each network mic is instead its own
PipeWire **client process**, `ctrlable-netmic@<name>.service`, running
`pipewire -c /etc/ctrlable-audio-manager/netmic/<name>.conf` against the
system daemon (proven on beta above: the stack was not restarted). The same
unit runs the session client that holds the device's control connection.
Adding or removing a network mic starts or stops one unit; nothing else moves.
The modules it loads:

```
# Generated by ctrlable_routing -- do not edit.
# rtp-mic=xvf3800-1-75357c room=dining
context.modules = [
  { name = libpipewire-module-rtp-source
    args = {
      source.ip = 0.0.0.0
      source.port = 46001              # one port per satellite
      sess.latency.msec = 80
      sess.ignore-ssrc = true          # the SSRC is new on every device boot
      sess.media = audio
      audio.format = S16BE             # L16 is big-endian on the wire
      audio.rate = 16000
      audio.channels = 1
      audio.position = [ MONO ]
      stream.props = {
        node.name = rtp_mic_xvf3800-1-75357c
        node.description = "XVF3800 Assistant 1 (Wi-Fi) - RTP beam"
        media.class = Audio/Source     # a source, never auto-linked to a sink
      }
    }
  }
  { name = libpipewire-module-echo-cancel
    args = {
      library.name = aec/libspa-aec-webrtc
      monitor.mode = true              # reference = the zone's monitor, no new sink
      audio.rate = 16000
      audio.channels = 1
      audio.position = [ MONO ]
      aec.args = {
        webrtc.high_pass_filter = true
        webrtc.noise_suppression = false   # leave NS/AGC to the XVF and the LVA
        webrtc.gain_control = false
      }
      capture.props  = { node.name = aec_mic_xvf3800-1-75357c.capture
                         target.object = rtp_mic_xvf3800-1-75357c node.passive = true }
      source.props   = { node.name = aec_mic_xvf3800-1-75357c
                         node.description = "XVF3800 Assistant 1 (Wi-Fi) - echo-cancelled" }
      sink.props     = { node.name = aec_mic_xvf3800-1-75357c.ref
                         target.object = zonebus_c0p1h4p3_dining node.passive = true }
    }
  }
]
```

Then `ctrlable-voice-assistant-next@<room>` with
`AUDIO_INPUT_DEVICE=aec_mic_xvf3800-1-75357c` if the server wake word is wanted.
The device is never told anything: the unit's session client connects to it
and sends `START 46001`.

## Delay alignment

The reference is tapped at the zonebus, BEFORE the room's output chain; the
echo reaches the server only after output latency + air + the XVF + I2S +
Wi-Fi + this receiver's buffer -- roughly 100-200 ms later. That is the right
direction (the reference must lead) and within what WebRTC AEC3's delay
estimator searches. Two things to watch:
- the rtp-source's rate matching drifts the delay by a few samples per second
  (measured above); AEC3 tracks slow drift, but a large `sess.latency.msec`
  change resets convergence -- pick one value and keep it;
- the dining room has no `tvmix_` bus; if a TV input is ever added there,
  add it as a second reference or it will not be cancelled.

Not yet measured: actual echo reduction with the real device in the room.
Use the soft-noise burst method from the USB XVF (`ctrlable-xvf-aecref`
header) on `rtp_mic_*` vs `aec_mic_*`.
